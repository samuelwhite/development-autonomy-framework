# Operator review for private hosting

The agreed topology is browser → authenticated HTTPS on Cortex → restricted reverse tunnel → Jarvis loopback → Mission Control container. HomeCI remains on its existing guest. The container makes read-only HTTPS requests to GitHub and needs no access to that guest or its administrative credentials.

## Preflight

The implementation environment could not read the live inventory. Jarvis SSH timed out and Cortex rejected the available SSH login. The example port is a local default and has no verified reservation on either host. An authorised operator must record both free ports, the unique Compose project name, the unused virtual host and the approved tunnel identity in private deployment records before issuing changes. Use the existing private Docker and Cortex configuration repositories or operator tooling for the final plan.

1. On Jarvis, inspect `ss -ltn`, `docker ps --format '{{.Names}} {{.Ports}}'` and `docker compose ls`. Include stopped services and pending changes from the operator inventory. Choose a free IPv4 loopback port and a unique Compose project name. Confirm that the Docker context targets Jarvis and that Engine is 28 or newer. Earlier releases have a known localhost publishing limitation. [Docker port publishing](https://docs.docker.com/engine/network/port-publishing/)
2. On Cortex, inspect `ss -ltn` plus the existing HTTPS virtual hosts, tunnel listeners and private DNS records through the established tools. Choose a separate free IPv4 loopback port and confirm that the intended virtual host has no owner or conflicting route. Check that the existing proxy can reach that loopback port from its own network namespace.
3. Confirm a supported certificate and access policy for the intended hostname. Prefer the existing authenticated private ingress with individual identities. Use application Basic authentication as an additional gate, or as the authentication mechanism only if the approved proxy policy allows it, passes the application's `Authorization` header and rate-limits failed logins. Never log authentication headers. If the proxy cannot preserve the application's Basic authentication, stop the rollout and agree a compatible ingress before proceeding. Do not expose a direct Jarvis listener or open a new firewall path.
4. Verify the existing reverse-tunnel convention. The private configuration should use the established managed SSH identity, host-key verification and service supervision. Request a remote forward with the shape `-R 127.0.0.1:<CORTEX_PORT>:127.0.0.1:<JARVIS_PORT>` and `ExitOnForwardFailure=yes`. Restrict the tunnel identity and its permitted listener to the one approved loopback destination. Confirm the actual listener binds only to loopback, accounting for the existing SSH daemon policy. Keep the tunnel key outside the container.

## Proposed deployment after separate approval

1. On Jarvis, stage the approved source revision and review and record the resolved base image digest in the private build or image-pinning workflow. Build the Docker image using `web/` as the build context. Keep the private Compose override and secrets outside the public checkout and build context. Set `DAF_PUBLISHED_PORT` to the verified Jarvis port.
2. Mount a required viewer password file plus an optional repository list and optional GitHub token as individual read-only Compose secrets or equivalent read-only file mounts. Point the container's `DAF_VIEWER_PASSWORD_FILE`, `DAF_REPOSITORIES_FILE` and `DAF_GITHUB_TOKEN_FILE` to their respective mounted files. Check the file ACLs from container UID 1000 without printing values. Omit environment variables for absent optional files. Grant no extra mounts, supplementary groups or capabilities.
3. Use the dedicated project name and both Compose files for every command. Run `docker compose ... config --quiet`, then `docker compose ... up --build --wait` after approval. Check `docker compose ... ps`, `/healthz` over loopback, and `401` for unauthenticated `/` and `/api/mission-control`. Verify that another machine cannot reach the Jarvis port. Restrict outbound network access to approved DNS and GitHub API HTTPS using the existing egress policy if available.
4. Bring up only the new managed tunnel through the existing private workflow. Verify the dedicated listener from Cortex and verify that a peer cannot reach it directly. Stage the single authenticated HTTPS route through the established change procedure. Preserve TLS verification and give upstream requests up to 20 seconds. Serve the page, assets and API behind the same policy. Route only the intended host and keep `/healthz` behind the private path or block it externally.
5. Validate TLS, the unauthorised response, and a valid viewer session in a new browser. Check the dashboard and job logs links, test a private source only if approved, and verify the expected unknown runner health. Inspect proxy and service logs for secret redaction and check existing virtual hosts. Record the image digest, source revision and network checks privately. Leave certificate renewal and route health to the established Cortex monitoring.

## Roll back

1. Withdraw only the new Cortex route through the established configuration workflow. Confirm the address no longer serves Mission Control.
2. Stop only the dedicated reverse tunnel. Confirm its Cortex loopback listener closed.
3. Use `docker compose ... down` with the recorded Mission Control project name and both Compose files. Verify the dedicated Jarvis port closed and existing services still respond. For an upgrade, the operator can restore the previously approved image and private configuration after the same loopback and authentication checks.
4. Revoke the dedicated GitHub credential if retiring the service or if exposure is suspected. Remove its private mounts and viewer credential using the normal secret-management procedure.
