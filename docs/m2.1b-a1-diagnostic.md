## Established defect and remaining uncertainty

The original probe made a synchronous 32-byte `ReadFile` call on a numeric handle
supplied by the parent, without first logging the handle, checking its object
type or establishing its identity. Its progress record came after the call.
That diagnostic design could block without explaining why. Microsoft documents
that [synchronous pipe I/O can wait indefinitely](https://learn.microsoft.com/en-us/windows/win32/ipc/synchronous-and-overlapped-input-and-output).

The retained original 131-byte output digest matches only the PID and three
standard-pipe records. It contains neither the attempted handle value/type nor
the read's return/error. A recycled standard pipe, invalid handle, unexpected
object or genuine inherited capability therefore cannot be established as the
historical kernel-level cause. The old attempt will not be replayed. The bounded
change addresses the established diagnostic defect, without claiming that a
particular object caused the original timeout.

## Repair and sensitivity

The diagnostic now records progress before duplication, metadata queries and
resource operations. It records numeric handles, validity, errors, object/file
types, standard-stream identity matches, intended-file identities and process
identity. No object names, arbitrary paths or resource contents are emitted.

Each valid handle is retained with a local `DuplicateHandle` before inspection.
The query uses a fixed 1,024-byte buffer and `NtQueryObject` **type information
only**; it never requests an unknown object's name. Microsoft warns that this
API may change, so an unavailable/failed/invalid response is an inconclusive
failure, without a fallback. See [the type query contract](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntqueryobject).
File handles additionally use file type, volume/file ID, regular-file attributes,
single-link status and the exact 32-byte fixture length. A synchronous read/write
is permitted only after that retained object identifies the intended finite
local synthetic file. File identity comparisons use the documented
[volume and file ID pairing](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info).

The probe distinguishes:

- Invalid handle: both handle-information and local duplication report Windows
  error 6. No resource operation was executed; this is evidence of no handle
  capability, not a successful `ReadFile` denial test.
- Approved standard-pipe alias: the retained object compares equal to exactly
  one standard stream, with file type PIPE. No read/write is attempted on it.
  This identifies a different authorized object, not the hostile fixture.
- Intended hostile file/process: the operation executes only after the exact
  file or PID/creation identity matches. Any such presence/access fails the case,
  including an operation returning a denial on the intended object.
- Unexpected live object, unidentified mapping/event, inconsistent metadata or
  missing progress: inconclusive failure. It is never counted as containment.

[CompareObjectHandles](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-compareobjecthandles)
compares underlying kernel objects without requiring object-specific access
rights. Numeric equality across processes is not used as object identity.

Before resume, the host independently duplicates the child's three specified
standard handles **out to the host**, confirms their object identities, and
examines the five hostile numeric slots the same way. Each valid slot is compared
against all five retained hostile objects and all three approved pipes. Any
hostile-object match prevents resume and fails the case. No host capability is
duplicated into the child. The original three-handle allowlist and all five
startup attributes pass through unchanged; an observer records and checks them.

Sensitivity is exercised inside the one diagnostic host invocation, before the
child launch. The same shared C++ inspection/operation code receives the actual
five host-owned handles as positive controls. It must read the R fixture, write
`!` to the S fixture, map and write `M` to its second byte, signal the event, and
use the process handle to duplicate and read the identified R fixture. The host
independently checks the two changed bytes and event state, then restores only
those explicitly permitted synthetic controls before launching the child.
Positive-control fields and effects are independently validated in Python.

This demonstrates the operation code's sensitivity on real objects in the host;
it does not pretend to be a deliberately leaked handle in the restricted child.
The inheritance allowlist is never expanded to inject a leak. Any inherited
mapping/event is detected by the host's object comparison; an unidentified live
mapping/event in the child is a failure without an unsafe speculative operation.
Independent Product review of this coverage and its limits remains required.

## One-execution boundary and evidence

Both native and Python entry points accept only `handles` / `probe` for A1. The
Python command requires `--a1-single`. A fresh, exclusive task-local claim file
is retained even on failure; it is an accidental-repeat guard, not a production
execution grant. The historical 20-case manifest remains reference data, and
the other 19 cases cannot reach process launch through the A1 runner.

Unknown output is never persisted. The reader accepts only bounded, allowlisted
numeric diagnostic records, retains safe partial progress before exit/outcome
validation, and refuses malformed, duplicate, missing or inconsistent records.
Original start, result and completion files are exclusive, flushed and read back.
A targeted completion always has `qualified: false`; one success can carry only
the label **"Targeted Gate A diagnostic passed provisionally."**

The restricted token, LPAC, fresh attempt identity, one-process Job, 128 MiB
memory limit, periodically enforced two-second user-CPU setting, ten-second wall
supervisor, parent deadline, output bounds, retained-process checks and cleanup
are unchanged. No ambient-read or CPU exception is broadened. The accepted
producer/verifier, native policy/contracts/evidence, desktop assets, dependencies
and workflows are not modified. `identity.h` and Gate B instrumentation are not
repaired or qualified as part of A1.

## Pre-execution validation

Eleven portable tests pass, with adversarial subcases for missing/duplicate or
malformed observations, false controls, genuine hostile-object matches, attempted
access, wrong bindings, unknown pipe identity, event modification and attempts
to invoke other native cases. These tests execute no native process. The same
tests require identity findings to remain explicitly distinct from I/O denial
claims. Repository lint/format and applicable existing regression checks are
required before the single fresh native case.

Before the native execution, repository Ruff checks and the distribution-boundary
check passed; all 42 existing portable native-contract/evidence tests passed.
The local Python suite completed with 451 passes and three existing symlink tests
skipped on this ordinary Windows host. An earlier portable invocation could not
write the tool sandbox's temporary directory (permission errors, including during
temporary-file cleanup); it was stopped. The successful invocation used a fresh
workspace temporary directory. No test or containment policy was relaxed.

Build preparation also retained two linker failures without executing a native
diagnostic: build 01 lacked the `CompareObjectHandles` import; build 02 selected
the documentation's `Kernelbase.lib`, which is absent from the installed SDK.
Inspection confirmed that the installed SDK's `OneCore.lib` provides the exact
symbol. The diagnostic links that import, resolved through
`api-ms-win-core-handle-l1-1-0.dll`, plus KERNEL32. The accepted producer/verifier
imports are unchanged. Build 03 compiled successfully but was not executed;
the final build includes strengthened portable evidence-consistency checks.
