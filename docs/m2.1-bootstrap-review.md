30 October 2026. **Stop for Product review. No M2.1 execution implementation.**

## Precise CPython failure

The actual unchanged M1.2 CPython 3.14.10 runtime's `python314.dll` statically
imports `BCryptGenRandom` from Windows `bcrypt.dll`. With WRITE_RESTRICTED:

1. Loader snaps identify `bcrypt.dll` failing during DLL_PROCESS_ATTACH.
2. A fixed NT-call trace observes `bcrypt.dll` at return RVA **0x81d5** calling
   `NtOpenFile` for **`\Device\KsecDD`**, requesting **0x00100003**
   (SYNCHRONIZE, FILE_READ_DATA and FILE_WRITE_DATA), share mask **7**, open
   options **0x20** (FILE_SYNCHRONOUS_IO_NONALERT).
3. Windows returns **0xc0000022 STATUS_ACCESS_DENIED**. The loader reports the
   failed attachment and the child exits **0xc0000142 STATUS_DLL_INIT_FAILED**.
4. An independent native probe, under the same composition, reproduces the
   denied read/write device open. Changing only the requested access to read
   plus SYNCHRONIZE succeeds. No device read, write or ioctl is issued. A normal
   `LoadLibraryExW` of the system bcrypt DLL fails with **1114**.

Thus the failing operation is an existing Windows crypto-device open during a
static dependency's initialization, before Python or the supplied probe runs.
The ordinary untraced CPython case fails identically. There is no patched DLL
return value, emulated success, pre-opened device handle or unsandboxed retry.
Granting this fresh SID access to the existing device is outside the permitted
investigation; its ACL was not changed. This is not a Windows vulnerability.

With the full restricting token (WRITE_RESTRICTED absent), CPython's loader
instead reports that opening **`\KnownDlls`** fails with STATUS_ACCESS_DENIED,
before application initialization. The minimal native child also fails to reach
its entry point under this full restriction, exiting 0xc0000022. No existing
KnownDlls permissions or broad restricting SID were added to make it start.

All final source, helper/child/runtime and relevant Windows DLL hashes are in
the evidence. The matching ntdll PDB identifies the loader-flag offset as 188;
it is discovered from symbols, not hard-coded. The system DbgHelp initially
failed the type query with error 87; the source-identified developer DbgHelp and
SymSrv copies supplied by the existing Visual Studio installation worked. The
LPAC information-class query also still returns 87; final-token checks and
contrasting real access checks establish only the measured LPAC semantics.

## Fresh native results

Environment: non-elevated ordinary account, Windows 11 Home x64 build
26300.9711 (26H2), existing development machine. The static native diagnostic
imports only Kernel32; other probe APIs load explicitly from System32 after
startup. Its built size is **160,768 bytes**; the no-CRT startup control is
**4,096 bytes**. These are unsigned maintainer probes, not distribution candidates.

The final matrix contains eleven cases plus two targeted supplemental
measurements (CPU repeat and full-restriction CPython tracing). No prior pass is
carried forward as a new pass. The original writable-profile negative-control
configuration is not reintroduced: these tests retain PR #12's sealed profile.

| Check | Fresh observation |
| --- | --- |
| Final token | Exact fresh restricting SID/package SID, low integrity, no elevation, change-notify only, registryRead only |
| AccessCheck intersection | Both package and attempt grants permit write; either missing grant denies it |
| Ambient write | Denied by native impersonation and running children; error 5, original SHA-256 unchanged |
| Explicit positive control | Native host-token probe and running children both write the generated dual-grant fixture |
| Permitted reads / host-private fixture | Permitted reads succeed; private synthetic host file and registry value denied |
| Profile, package root, TEMP, workspace, copied runtime writes | Denied, including append and tested owner/DACL bypasses |
| Registry writes / WRITE_DAC | Denied; machine version read succeeds |
| Profile recreation | API returns error 87; subsequent file/TEMP/registry writes remain denied; not relabelled as access denied |
| Synthetic Credential Manager entry | Error 1702, no credential returned; not relabelled as access denied |
| Synthetic host DPAPI blob | Decryption denied, error 5 |
| IPv4 loopback and TEST-NET TCP/UDP | Error 10013; DNS returns 11003; no claim of exhaustive network API or packet-capture qualification |
| Child creation / breakaway | Denied with 367 / 5 |
| Memory | 32 MiB allocation succeeds; 160 MiB is refused with 1455 under the 128 MiB limit; host commit headroom exceeded 23 GB |
| CPU | Configured two-second user-CPU limit causes kernel exit 0xc0000044, but actual user CPU is **4.4375 s**; repeat **8.421875 s** |
| Wall deadline | Idle child terminated at the ten-second supervisor deadline; about 10.24 s including setup |
| Helper killed | Retained child process handle becomes signalled in about 0.005 s |
| Supervising parent killed | Helper detects parent death; both retained process handles become signalled in about 0.030 s |

The CPU result proves termination, **not a two-second hard ceiling**. Microsoft
documents [periodic checks of accumulated user time](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information).
No job limit or watchdog setting was changed to hide the overrun. The separate
ten-second wall deadline remains. A future authority/resource contract must
state an acceptable bound; a strict two-second cap is not qualified here.

## Read isolation is a separate decision

The running native child can read the low-integrity fixture exposed to
ALL_RESTRICTED_APPLICATION_PACKAGES, despite it having no attempt-SID grant.
WRITE_RESTRICTED blocks its write but does not narrow every ambient read grant.
LPAC still excludes the contrasting ALL_APPLICATION_PACKAGES access and denies
the tested private host file/registry/credential paths. These facts do not turn
LPAC into a per-attempt read allowlist. Windows/shared-runtime resources remain
accessible where the LPAC access model allows them.

The full-restriction variant would require the additional SID check for reads,
but does not initialize even the minimal native child in this configuration.
It is not a usable stricter alternative demonstrated by this investigation.
No arbitrary file grants, system ACL changes, broad SIDs or administrator setup
were substituted for it.

## Decision-ready comparison

| Option | Evidence and usefulness | Remaining decision / cost |
| --- | --- | --- |
| Native deterministic worker for M2.1 | Starts without CNG/Python bootstrap; small static executable; fresh write, process, memory, lifecycle and network observations support further design review for the one-file deterministic patch task | Does **not** meet strict per-attempt read isolation or a hard two-second CPU ceiling. Product/security must explicitly decide whether the documented LPAC read exposure and periodic CPU enforcement are acceptable. The actual adapter and all approval/journal/verifier integration remain unimplemented. |
| Stronger separate isolation architecture | Could provide an independently controlled OS/resource boundary for future broader workers | No such architecture has been tested here. Needs a new prerequisite, Windows Home/non-admin compatibility, installation, memory/startup cost and lifecycle assessment. Do not assume a VM/container product satisfies the current no-admin requirement. |
| Defer execution | Preserves the useful, genuine M1.2 read-only GitHub planning workflow without claiming new authority | No executable development task yet. Lowest immediate implementation and qualification burden; keeps the original strict requirements intact. |

Recommendation: **retain the implementation block**. The native worker is now a
credible narrow design option, not a qualified implementation foundation for
every original boundary. If strict per-attempt reads and a hard two-second CPU
ceiling remain mandatory, choose deferral while reviewing a stronger isolation
architecture. If Product accepts the measured boundary explicitly, revise and
approve the M2.1 design before implementation. Do not keep adjusting this final
bootstrap experiment or silently relax either requirement.

Host-owned exact-byte approval, single-use short-lived nonrecoverable authority,
GitHub plan/scope versus local replacement provenance, separate production and
verification, durable evidence, Stop/recovery and patch-only output remain
mandatory for any later approved implementation. No imported plan, successful
test or stored report grants execution or spending authority.
