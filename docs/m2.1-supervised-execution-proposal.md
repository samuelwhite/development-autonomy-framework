# M2.1 proposal: one supervised local documentation change

30 October 2026. **Conditionally approved; implementation blocked at the Windows
isolation feasibility gate.** See [the measured blocker and design review](m2.1-isolation-review.md).
Foundation: [verified M1.2 integration](m1.2-integration.md), main
`5b6f5d4328854df66d7bc25ab7aa0504256e6e12`.

## Recommended capability

A user selects one real GitHub-planned documentation correction, reviews the
exact before/after text and grants one short-lived local execution approval.
DAF produces the changed file in a fresh isolated workspace, independently
checks the result, and presents a durable diff and evidence for human review.
It can save a patch through a separate native Save dialog. It never applies that
patch to the user's repository, commits, pushes, opens a PR or advances a plan.

The first adapter is a deterministic single-block UTF-8 replacement. It is a real
file change, not a simulated worker or AI-generated answer. Limiting the action
to a reviewed edit makes scope, verification and recovery testable before adding
a general coding agent. Codex/Claude sessions, repository scripts, package
installation and provider costs are outside M2.1. This deliberately precedes the
broader M2 bounded-Codex objective rather than claiming that objective is complete.

Windows 11 x64 is the proposed execution target. Linux retains M1.2 read-only
planning and the demo until equivalent execution isolation is separately qualified.
No administrator prompt, Docker, WSL, VM, system Python or terminal is required.
If the required Windows isolation cannot be established, execution refuses.

## Authority model

| Event or record | What it permits |
| --- | --- |
| GitHub plan import / structural validation | Viewing an untrusted proposal only |
| Explicit public-read consent | Bounded source preparation; no edit |
| Prepared diff and successful preflight | Asking for human approval; no edit |
| Native approval of an exact change | One local attempt, within the displayed policy |
| Worker exit or supplied receipt | Untrusted output; no verified success |
| Independent local verification | A candidate ready for human review; no next task |
| Human acknowledgement / patch export | A review observation / saving that artifact; no repository apply |
| Application restart | No restored execution grant |

The approval principal is the current interactive Windows user, observed by the
trusted native host. This is not proof of GitHub ownership, an organisation's
review authority or resistance to malicious same-user UI automation. No local
signature is claimed to establish those properties. This scope is suitable only
for a private local candidate; a shared or remotely approved executor needs a
separate authenticated authority design.

Product's mandatory refinement: the native host must show the exact independently
verified before/after bytes, exact path, scope and manifest digest through its
own trusted review surface. The ordinary renderer cannot provide that surface,
substitute its displayed content, or change the candidate after review. The
approval binds to precisely the bytes the trusted host reviewed. Keep the grant
single-use, short-lived and nonrecoverable after restart. This surface is not yet
implemented; the failed isolation gate prevents proceeding to it.

The GitHub-pinned task defines the planning source and permitted scope. A local
change specification supplies replacement bytes separately. Every preparation
and native review must identify that distinction: GitHub did not approve locally
supplied replacement text. Native approval authorises the exact candidate
independently; plan import, proposal acceptance and successful tests grant nothing.

The host creates a random session nonce and holds a one-use grant only in memory.
Bind it to the OS user, app/adapter/verifier/policy versions, plan source and all
content digests, proposal ID, baseline, change digest, workspace identity,
attempt ID, stop epoch, exact limits and five-minute monotonic expiry. Native
Cancel is the default. A changed binding invalidates the entire grant. The
renderer cannot supply grants, expiry, approval flags, environment or executable
paths. Closing, reload, Stop, cancellation or restart revokes pending grants.

Persist an approval **observation** and consumed grant digest for audit, never a
reusable bearer token. A database row saying approved cannot start work. Source
budget fields remain inert metadata; the effective policy has provider requests,
tokens and monetary authority fixed to zero. Positive paid authority is refused.
Neither the fixture approval marker in `Plan` nor a PR #7 receipt is accepted by
the execution admission path. Its historical `supervised_codex` bundle label is
not a dispatch instruction; the new adapter is explicitly identified separately.

## Preparation and isolated workspace

Use a fresh app-owned attempt directory under `execution-v1`, separate from
`planning-v1`, v0.1 synthetic journals and all user checkouts. Do not clone or use
a Git worktree in this first slice: shared Git metadata, hooks and checkout
filters add capabilities this task does not need. Materialise a bounded partial
snapshot of named regular blobs only; do not call it a full repository checkout.

Preparation requires a new source-specific native read confirmation. Re-fetch
the complete plan at its exact source commit and compare it with the retained
snapshot. At the exact baseline commit, obtain the target plus every declared
protected file/workflow through pinned tree/blob reads. Resolve no branch or tag.
Verify supplied hashes against actual bytes. Missing, mismatched, oversized or
unsupported dependencies refuse; never turn missing evidence into success.

Only one dependency-free milestone and one exact existing `.md` file beneath
`docs/` are eligible. The effective scope is the intersection of that task's
scope, complete-plan boundaries and a fixed DAF deny policy. Always deny Git
metadata, workflows, security policy, licences/notices, dependency/configuration
files, `AGENTS.md`, `CLAUDE.md`, `CODEOWNERS`, `.codex`, `.agents`, `.claude`, private
and infrastructure paths, even if an imported plan omits protection. Compare
case-folded components, preserving exact Git spelling. Deny traversal, device and
UNC paths, mapped/remote volumes, ADS, 8.3 aliases, case collisions, reparse points,
symlinks, hard-link aliases and nonregular files. No renames, deletion or mode edits.

For policy version 1, deny any directory component equal (case-folded) to `.git`,
`.github`, `.codex`, `.agents`, `.claude`, `private`, `infrastructure`, `terraform`
or `ansible`, and any basename equal to `agents.md`, `claude.md`, `codeowners`,
`security.md`, `license`, `license.md`, `license.txt`, `notice`, `notice.md` or
`notice.txt`. Non-Markdown configuration/dependency files are already outside the
allowlist. Union these restrictions with all source-declared protected paths;
never weaken the fixed policy by changing a plan. Display control and bidi
characters visibly escaped in the review without changing their hashed bytes.

The trusted broker owns filesystem writes. A small Windows native helper must
open and retain directory/file handles, check final volume/file identities and
reparse/link state, and perform create-new writes beneath those verified handles.
A string prefix check followed by an ordinary path open is insufficient. Baseline
and sealed input files are read-only; producer and verifier cannot alter them.
No writable hard link to a source, evidence file or another attempt is allowed.

Preflight constructs an immutable review manifest and exact diff. The old block
must occur exactly once; preimage and expected result hashes must match. A source
instruction can be displayed but is never parsed into commands. Declared GitHub
checks remain pending/unverified unless independently collected by a separately
approved feature. Local verification cannot satisfy or rename those checks.

## Execution and independent verification

Keep the M1.2 read-only process and renderer restrictions intact. Add a separate
fixed execution controller, launched only for preparation or an explicit attempt;
it is not a daemon or network service. Reuse the bundled Python runtime, but never
load repository modules, user site packages, hooks, MCP settings or environment
credentials. Use fixed entry points and isolated interpreter settings.

Recommended Windows boundary: a small bundled native helper using a
Less-Privileged AppContainer, no network/device/credential capabilities, and a
Job Object assigned at process creation. Allow only the named runtime files and
explicit inherited stdio handles. Deny child creation and breakaway; set
kill-on-close, memory and CPU limits. Use separate producer and verifier
identities. The worker receives bounded bytes, not workspace paths, and returns
candidate bytes over a bounded pipe. Only the broker can materialise the admitted
candidate file. Neither child can access the journal, stop store, grants, host
profile, user checkout or the other's output.

Microsoft documents [AppContainer isolation](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation),
[LPAC launch](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer),
[process security/handle/job attributes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute)
and [Job Object lifecycle controls](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).
These support the proposed mechanism, not a claim that DAF has implemented or
qualified it. In particular, an AppContainer has its own writable profile by
default. The helper must restrict that profile and registry storage too; a
workspace ACL alone cannot establish the proposed no-filesystem-write child.

Implement this helper with a small Win32 C++ surface and no new runtime service;
bundle it with the app. It accepts only named policy/adapter IDs and resolves fixed
packaged entry points, never caller-supplied executables or command lines.
Qualify the exact compiler/runtime/OS combination before
enabling execution. A folder, `cwd`, Python flags or a Job Object alone is not a
filesystem/network sandbox. Unsupported isolation or ACL setup must refuse;
there is no same-user unsandboxed fallback. Malicious administrators, a compromised
OS/broker or replaced application binaries remain outside this local threat model.

The producer implements only literal single-block replacement. The broker treats
its result as untrusted, bounds its size and stages it without a success label.
After the producer is confirmed exited, seal the candidate read-only. A fresh
verifier, with a different entry point and no producer write access, must:

1. Revalidate the approved manifest, original bytes, source/task bindings and
   complete materialised file inventory.
2. Independently locate the unique old block and compare prefix, replacement and
   suffix byte ranges. Do not call the producer's transformation function.
3. Recompute the complete diff and hashes: exactly one permitted file changes;
   every other materialised/protected file is identical; no modes, links or extra
   files appear. Verify the expected candidate hash as an additional check.
4. Check the named acceptance rules and return a closed result tied to the exact
   attempt, manifest, candidate and validator build. Repository tests never run.

The broker binds evidence to its owned verifier process and authenticated pipe
origin, validates the response, and rechecks sealed bytes before committing the
result. A worker's success claim, a supplied JSON receipt or exit code zero alone
is insufficient. Independence here means separate process, privileges and checking
logic, not external CI attestation or proof against every shared software defect.

## Versioned local operations

Use a separate `execution` protocol version 1; do not widen M1.2's existing
planning operations. Implement closed JSON Schemas on both sides, independent
runtime validation, exact sender/main-frame checks and typed preload methods.
Unknown fields, schema majors, operations and enum values refuse.

| Operation | Renderer input | Host-owned effect |
| --- | --- | --- |
| `describeCapability` | none | Report supported policy/isolation; no task launch |
| `prepareChange` | snapshot ID, milestone ID, exact change specification | Native read consent, bounded preparation and diff; no grant |
| `requestRun` | candidate ID, expected manifest digest | Native approval, fresh one-use grant, one attempt |
| `getAttempt` / `listAttempts` | attempt ID / bounded cursor | Read and revalidate local history; no execution |
| `stopAttempt` | attempt ID | Durable stop, revoke grant, terminate owned job |
| `reinspectAttempt` | attempt ID | Explicit verification-only permission; never rerun producer |
| `exportPatch` | attempt ID | Native Save dialog, revalidate and create one patch file |

Every request carries protocol, host-generated request ID and operation. Request,
candidate and attempt IDs are 32 lowercase hex characters. Snapshot/proposal IDs
and hashes are 64 lowercase hex characters; commits are full Git SHAs. Milestone
IDs retain M1.1's portable identifier rules. Renderer requests are capped at 32 KiB,
responses at 1 MiB and history pages at 20 items; child input is capped at 256 KiB.
The change specification has exactly `path`, `beforeSha256`, `oldBlockBase64`,
`newBlockBase64` and `expectedAfterSha256`. All three byte sources must be strict
UTF-8 text without NUL, preserve line endings, and differ. Base64 is canonical.
The manifest additionally binds all source/blob/content/proposal references,
baseline inventory, effective scope, policy/adapter/verifier/build IDs, resource
limits and workspace identity. Hash canonical JSON using DAF's existing canonical
encoding rules; publish shared JS/Python conformance vectors.

Results contain request/attempt IDs, monotonic event sequence, typed state and
fixed refusal codes. Never accept a supplied trusted/approved flag. No generic
command, arguments, working directory, URL, path-to-open, callback or IPC channel
is exposed. Save destinations come from the native dialog only; reject existing
files, links and remote volumes, and never apply the patch as part of export.

## Admission, evidence and recovery

Use a new execution journal with its own application/schema ID. Preserve v0.1's
synthetic engine and fixture ledger rather than silently turning them into live
authority. Reuse reviewed pure validators and stop-control invariants; add an
explicit admission layer and tests before composing them with real side effects.

Obtain one controller exclusion lock. Under the short durable stop fence, verify
the live grant, source/manifest bindings, stop epoch and limits; consume the grant
once and commit an admission/launch intent. Do not hold the fence over network
reads, user prompts, worker execution or verification. Launch the contained process
suspended, with job membership established at creation; recheck the stop state
before allowing it to run. A stop committed before admission permits no new
admission. An already admitted operation may be in flight; cancellation does not
claim to undo completed writes.

SQLite and OS process creation are not one atomic transaction. A crash after
intent but before recorded launch is `outcome_unknown`, never proof of absence
and never permission to replay. Record process identity including creation time,
not PID alone. The native helper owns noninherited kill-on-close job handles;
parent-pipe loss and hard deadlines terminate owned descendants. A watcher must
also cover the controller/helper relationship, not only the leaf worker.

The journal retains append-only source observations, approval observations,
admission IDs, stop epochs, launch/exit observations, source and artifact hashes,
bounded logs, verifier version/results and human review/export events. Store full
source and before/after bytes separately with no-overwrite atomic publication.
Use `synchronous=FULL`, short transactions and unique admission/attempt bindings.
Triggers and hash chains detect accidents/inconsistency; they do not authenticate
a same-user-rewritten database or prevent backup rollback.

```text
proposal -> prepared -> awaiting native approval -> admitted -> running
          -> candidate sealed -> independently verified -> ready for review
any active state -> stop requested -> stopped confirmed | outcome unknown
crash/restart -> interrupted, all grants revoked -> inspect/reverify or abandon
```

Stop first attempts a durable fence and invalidates all pending decisions, then
kills the owned job and waits for confirmed exit. If persistence fails, still
attempt termination but report `stop_not_durable` and prohibit new admission.
If exit cannot be confirmed, retain `outcome_unknown`; never show safely stopped.
Late output cannot change a stopped attempt into success. Partial/staging files
remain incomplete and are never exported as verified results.

On reopen, validate records and artifact hashes before display; show retained
observations with their actual trust level. Reinspection requires explicit
verification-only consent and can produce a recovered candidate for review, not
a restored grant. Retry requires a fresh native approval, attempt ID and workspace;
it never overwrites the original or resets an old allowance. No automatic retries,
resume, dependency advancement or cleanup of unresolved evidence.

## Fixed limits for this slice

| Resource | Proposed enforced maximum |
| --- | --- |
| Execution concurrency / retries | One attempt; zero automatic retries |
| File changes | One existing regular UTF-8 Markdown file |
| Baseline/target/result file | 64 KiB each; source plan retains M1.1's 64 KiB limit |
| Old/new replacement blocks | 8 KiB each, one occurrence |
| Prepared source | At most 16 blobs / 2 MiB, 64 GitHub GETs with 192 KiB response caps and 60 seconds overall; explicit read only |
| Producer / verifier | One process each, sequential; 128 MiB job memory, 2 CPU seconds and 10 wall seconds each |
| Complete execution attempt | 30 seconds; independent parent deadline of 35 seconds |
| Child candidate response / logs | 128 KiB / 16 KiB per stream; overflow terminates |
| Attempt artifacts | 4 MiB broker-written; children have no filesystem write permission |
| History | 100 attempts/preparations / 256 MiB including retained staging files; full means refuse |
| Provider/credential/repository-write authority | None; zero requests, tokens and monetary allowance |

Enforce output/storage bounds before writing, and reject unsupported AppContainer
profile confinement rather than claiming a disk bound that excludes its writable
profile. Job limits are kernel-enforced where supported; wall deadlines, bounded
pipes and broker writes are independent controls. Do not silently widen limits
on a slow machine. Changes to this policy require a new review and grant.

AppContainer profile IDs are random, application-owned and recorded by the host.
After confirmed process exit, remove only the verified owned profile and its
temporary ACL grants; keep all attempt evidence in the separate journal store.
Failed cleanup is reported and retried only against recorded identities. Never
delete an unknown profile, erase unresolved evidence or kill a reused PID.

## Product decision status

Product conditionally accepted the deterministic documentation-only task,
patch-only output and authority model, subject to the trusted-review refinements
and a passing standalone Windows isolation gate. That gate failed. No execution
controller, grant, adapter or desktop execution workflow has been implemented.
The next decision is the isolation design review linked above; this approval does
not provide standing execution/spending authority or permission to distribute.

If the required first capability instead includes an AI-authored code change or
running repository tests, this proposal is insufficient: provider identity,
independently enforced spend exposure, hostile-code containment and runner trust
must be designed and approved first. Do not substitute those capabilities silently.
