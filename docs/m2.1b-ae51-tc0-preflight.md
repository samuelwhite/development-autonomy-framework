## Public route, approval and single-use claim

`ae51_tc0.py` accepts exactly one reviewed package path and calls the public
`ae5_parent.native_entry`. The existing Python gate refuses before imports or
I/O. The public executor and collector also require the Python/Windows gates
and a nonempty source-controlled Product decision identifier; the executor
checks the frozen C++ release literal before claiming an attempt. All remain
closed. There is no activation flag, environment override, dynamic loader or
alternate case selector. Recovery remains separately disabled.

A future release requires a separate Product decision, minimal explicit source
release, a fresh frozen build and package, and an approval record bound to that
package's exact source commit/tree, generated sources, executable hashes,
manifest, exercise and TC-0 identity. The record specifies one attempt, zero
retries, decision ID, not-before and expiry. It is checked before claiming,
after claim persistence and again immediately before helper creation. A digest,
test pass or schema validation is never approval. The approval record's origin
depends on the trusted Product/source-review process; this is not a general
cryptographic approval service or production grant mechanism.

The fixed claim path is `dist/m21b-ae51-TC-0-consumed.json`; the attempt directory
is `dist/m21b-ae51-TC-0`; irreversible STOP is
`dist/m21b-ae51-STOP.json`. Exclusive creation, flush/fsync and exact readback bind
the consumed claim to the approved package and approval bytes. Existing or
partial files consume the attempt; choosing another output directory cannot
reset it. The collector requires that exact durable claim and an exclusive
collection-start record. No such paths were created during this preflight.
Tests use in-memory synthetic observation/invalid-claim models; they do not
create successful native claims or receipts.

Only fixed synthetic fixtures, four hash-pinned binaries and the owned attempt
directory are prepared. Before helper creation, retained read handles deny
binary write/delete sharing and verify bytes, canonical paths and file
identities. This diagnostic check does not qualify Gate B or implement production
execution admission. The existing outer Job, inner Job and restrictions remain.

The temporary parent snapshot process handle uses `0x1450`
(QUERY_INFORMATION, QUERY_LIMITED_INFORMATION, VM_READ, DUP_HANDLE), verifies its
actual grant and closes before ACK. It is derived only from the retained owned
child handle; no arbitrary PID is opened. The parent already retains the trusted
helper's duplication capability during handoff. This is temporary diagnostic
observation authority, not a change to the child's token or accepted inheritance
policy. Availability of these rights on the actual restricted child remains a
native qualification question; failure refuses ACK rather than broadening rights.

PSS flags 132 capture handles and threads, with context flags zero: no VA clone,
memory dump, thread context or object-name capture. SDK structure sizes/offsets
are compile-asserted (handle entry 136, thread entry 120, suspend offset 108).
Only bounded identities, values, counts and masks are recorded. See Microsoft's
[capture API](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/nf-processsnapshot-psscapturesnapshot),
[capture flags](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/ne-processsnapshot-pss_capture_flags)
and [thread entry](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/ns-processsnapshot-pss_thread_entry).

The verifier is separate from the native helper, but deliberately runs in the
trusted Python parent and uses retained handles. This is not independence from
a compromised parent, OS or privileged external mutator. A pre-ACK suspended
snapshot alone cannot prove a child was never resumed later; that claim also
requires the reviewed no-resume implementation, complete original record and
expected fixed-child exit. These are explicit threat-model assumptions.

## Deadlines, failure and cleanup

The original 5000 ms inspection, 3000 ms termination, 10000 ms runtime and 30/35
second helper/outer bounds remain. Setup/handoff and the new witness are charged
to the original absolute budgets; insufficient remaining time refuses ACK. The
runtime deadline exists unchanged but remains unreachable because no child can
resume. The setup watchdog starts before helper creation. The custody safety
lane does not depend on the protocol/ledger lock or blocked IPC, inspector,
fsync, cleanup or normal helper exit. Child and outer-Job termination requests
use separate one-shot lanes. A separate collector lane enforces the outer bound
while preparation/readback/persistence work is blocked.

STOP cannot be undone by late ACK, late inspection, late persistence or duplicate
completion. A normal empty EOF after cleanup ACK ends capture only; early or
partial EOF refuses. The 30-second helper deadline remains active if normal
shutdown stalls. Termination requests, returned API results, retained-handle exit
confirmation, tree quiescence and cleanup confirmation remain separate facts.
Failed/pending termination calls and safety-query failures prevent success. Only
when the child is independently already signalled is a redundant TerminateProcess
omitted; outer containment still closes the tree. Microsoft documents both the
asynchronous nature of termination and ERROR_ACCESS_DENIED on an already
terminated process in [TerminateProcess](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess).

After confirmed exits/quiescence, safety and termination lanes must finish before
request results are frozen. The finalisation latch rejects late/duplicate
completion, including persistence completing after revocation. A receipt file
alone is insufficient: the completion record, absence of STOP/incomplete evidence
and successful bounded public-runner completion are also required. An interrupted
parent or uncertain final persistence is unresolved even if a receipt exists.
Claim consumption prevents a replacement attempt. OS scheduling, Python progress
and functioning kernel calls remain assumptions; arbitrary kernel/driver stalls,
power loss, filesystem failure or a frozen trusted parent are not universally
interruptible or durably recoverable within these bounds.

Diagnostic normal teardown now restores only recorded fixture grant/label
descriptors, in reverse order, through retained exact handles (maximum 64).
Independent readback compares original identities and descriptors. This closes a
normal-sham cleanup gap in the earlier compile-only tooling; it does not activate
the separate recovery adapter. Synthetic positive-control append and protected
fixture ciphertext are explicitly expected and independently bound. Other
fixture bytes must match. No recursive or broad deletion is performed. Unknown
cleanup remains quarantined with ledger/evidence for a separate Product decision;
no recovery or next case is attempted.

## Proposed single-case decision

Product must separately decide whether to authorise the minimal source release,
fresh frozen compile/identity review and **TC-0 once, zero retries**. Current
preflight package/binaries remain closed; their bytes cannot be silently activated.
A future release package must carry its new identities and explicit approval,
while preserving the package above. No runtime switch substitutes for that review.

The precise proposed public command, from the repository root after that separate
release/preflight, is:

```powershell
C:\Python314\python.exe -B desktop/native-prelaunch/ae51_tc0.py dist/m21b-ae51-release-01/TC-0-package.json
```

That future package does not exist and this command has not been executed. The
only proposed case is the custody sham: prepare the fixed fixtures, establish
creation-time outer/inner custody, observe the suspended child independently,
close temporary authority, ACK, run unchanged inspection, terminate without resume,
require normal helper exit, confirm tree quiescence and exact cleanup, then verify
and durably bind the original evidence. Every criterion above is mandatory.

Any preflight identity/gate mismatch prevents a claim/launch. Once claimed, any
unexpected result, API refusal, missing/partial evidence, late ACK, deadline,
forced helper termination, unconfirmed exit, uncertain cleanup or interrupted
completion consumes the attempt and stops progression. No repair-and-rerun,
replacement attempt, implicit approval or recovery is allowed.

Windows rights/PSS availability, real Job nesting and timings, normal resource
restoration and all live custody behaviours remain untested by this preflight.
Parent death, helper stall/death, deliberate communication loss and cleanup
obstruction require their separate controls. TC-1 through TC-8 remain an inventory,
not an approved budget. Continuation/wrong-pipe/A2-16/A2-17, Gate B and all production
capabilities remain gated. Stop for Product review; no merge, release, tag or
binary publication.
