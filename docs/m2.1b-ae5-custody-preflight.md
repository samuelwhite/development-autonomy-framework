## Implemented custody boundary

The Python parent creates an unnamed, non-inheritable outer Job. A fixed native
helper enters it at creation through `PROC_THREAD_ATTRIBUTE_JOB_LIST`; there is
no running-helper/post-creation-assignment gap. The parent remains outside that
Job. Unknown existing ancestor-Job restrictions are refused rather than escaped.

The outer Job has kill-on-close, a two-process ceiling and no breakaway. The
unchanged inner Job retains its one-worker ceiling, 128 MiB process memory and
20000000 100-ns units of process CPU time. The child retains all existing token,
LPAC, restricting-SID, integrity, mitigation and three-pipe constraints.

Parent-held rights are checked using bounded ObjectBasicInformation observations:

| Object | Retained access |
| --- | --- |
| Helper process, stable supervision handle | `0x101001`: terminate, limited query, synchronize |
| Helper transfer handle, temporary | `0x40`: duplicate handle; closed before inspection ACK |
| Child process | `0x101001`: terminate, limited query, synchronize |
| Primary thread observation | `0x100800`: limited query, synchronize; no resume right |
| Inner Job observation, temporary | `0x4`: query; closed before inspection ACK |
| Outer Job after setup | `0xC`: query and terminate |

Creation returns the helper's original process object. The parent pulls the
child and thread objects from that helper's retained creation handles; it does
not reopen arbitrary PIDs. It checks PID/creation time, thread ownership, image
path, Job membership, exact queried limits, granted rights and inheritance flags.
Ownership of the outer Job is established by its closed construction and absence
from exported/inherited handles, not by a claim to have scanned every process.
Real last-handle behaviour remains a native qualification requirement.

A fixed, sequence-bound 64-byte ACK carries the exercise, parent identity and
absolute deadline. The helper cannot start the unchanged inspector until the
parent has verified custody, closed its temporary handles and acknowledged.
The shared inspector and its acceptance predicate are included unchanged. The
generated harness calls an always-terminating inspection wrapper; its original
resume call is replaced by an unconditional diagnostic refusal.

## Supervision and evidence

The setup watchdog is armed before helper creation. The custody supervisor has
no dependency on the IPC/ledger lock, stderr drain, persistence or cleanup. Child
termination and outer-Job termination use separate one-shot lanes so a blocked
termination call cannot prevent the other request. The safety lane does not join
a blocked inspector or require a normal helper exit.

STOP is irreversible. Late evidence cannot re-establish custody or rearm a
deadline. The 5000/3000/10000 ms constants and 30/35-second absolute bounds remain
unchanged. Setup/handoff time is charged to the original parent budget; inspection
ACK is refused when insufficient time remains. The 10000 ms runtime path remains
unreachable. Windows ACK timestamps use GetTickCount64, not a different clock epoch.

The parent independently drains helper stderr. Helper control frames retain the
existing 65624-byte aggregate stdout capture ceiling; stderr remains capped at
32768 bytes. Each frame is at most 32768 bytes, at most 256 messages are accepted,
and descriptors are capped at 8192 bytes. Original bounded control/stderr prefixes
and sent ACK bytes are retained even on truncation or refusal. These are diagnostic
host messages; the worker's existing input/output contract is unchanged.

The independent schema distinguishes termination requested, confirmed exits,
tree quiescence and cleanup confirmation. A successful termination request alone
cannot establish any later state. Unknown outcomes are UNRESOLVED. Native-mode
verification requires separate live readback and cannot launch additional processes.
Parent-death observations require complete retained membership and a witness with
zero inner/outer Job handles. Schema acceptance is not a case-pass receipt or
execution authority.

## Exact-resource ledger and recovery limits

Before each profile, credential, registry or private-desktop creation, and before
fixture/profile ACL or integrity-label changes, the helper requests a durable
parent-owned intent ACK. The parent independently checks the resource scope and
records original descriptors and object identities. A separate commit records
the operation outcome. Exclusive writes, fsync/readback, sequence and digest-chain
checks refuse overwritten, nested, incomplete or failed transactions.

The dormant recovery adapter first requires confirmed process exits and outer
Job quiescence, plus an exact match between the ledger and retained resource
inventory. It restores only matched descriptors, rejects changed file identities,
links and unexpected registry contents, and removes only the recorded synthetic
credential/keys/profile. It does not perform recursive filesystem deletion.
Profile removal uses DeleteAppContainerProfile and requires absence readback.
The existing explicit host-user ACE remains intact; no restricted-child ACL is
weakened to permit cleanup.

An interrupted transaction, unavailable registry object identity, unexpected ACL
state or unconfirmed exit prevents automatic recovery. The ledger and resources
remain quarantined for explicit review. In particular, this is not an automatic
post-parent-death recovery service: lost live registry identity is refused, and
the external witness/recovery arrangement for TC-5/6 still needs a dedicated
preflight. A recovery operation cannot promote the original failed attempt.

## Proposed conditional qualification sequence

No attempt is released. A separate source-controlled native-entry/claim/receipt
preflight and fault-control/witness preparation are required before execution.
Do not invoke private adapter methods, patch gates, or treat these components as
a runnable qualification collector. The public entry deliberately refuses.

Proposed maximum: **nine fresh custody attempts, one per control, fixed order,
zero retries**. Each tests a distinct boundary; combining the before/after-custody
parent-death cases would leave one lifecycle window unobserved.

| Control | Independent acceptance requirement |
| --- | --- |
| TC-0 custody sham | Actual identities/rights/nesting; temporary handles closed before ACK; unchanged three-pipe inspection; zero resumes; child terminated; helper exits normally; complete cleanup |
| TC-1 wrong-Job offer | Valid unrelated owned Job rejected by actual membership checks; no inspection ACK; confirmed termination and cleanup |
| TC-2 incomplete handoff | Owned child exists while ACK is withheld; setup/outer deadline terminates helper and child; no inspection or resume; cleanup confirmed |
| TC-3 inspection/shutdown stall | Controlled inspector and helper shutdown non-cooperation; parent revokes at five seconds and independently terminates both; forced helper exit distinguished; exact-resource recovery/readback succeeds |
| TC-4 helper death | Unexpected helper death causes STOP; child/process-tree termination independently confirmed; no late permission; cleanup confirmed |
| TC-5 parent death before ACK | External process-only witness confirms last-outer-handle containment of helper and suspended child; no retained Job handle; exact cleanup independently resolved |
| TC-6 parent death during inspection | Same proof after custody while helper/inspector cannot cooperate; witness/recovery preflight is a prerequisite |
| TC-7 communication loss/late result | Genuinely completed result delayed past STOP cannot change the actual decision; no resume; termination and cleanup confirmed |
| TC-8 cleanup obstruction | Exact owned obstruction produces explicit unresolved cleanup, no clean receipt and no next case; separately approved exact-resource recovery appends evidence without relabelling the failure |

Release TC-0 first only after its activation/preflight decision. Every subsequent
case requires the preceding independently verified durable receipt. Unexpected
results, missing evidence, overruns, wrong object identities or uncertain cleanup
consume that attempt and stop the allowance. No repair-and-rerun or replacement
attempt is implied. TC-5/6 and TC-8 remain conditional on their additional witness
and recovery preparations.

Real Windows nesting, rights, parent-death behaviour, forced shutdown and recovery
have **not** been demonstrated by this compile-only exercise. The trusted parent,
OS and scheduler assumptions remain. NtQueryObject layout availability, inherited
ancestor Jobs, resource collisions and evidence caps can cause refusal. Kernel or
driver stalls, power loss, privileged external mutation and arbitrary parent hangs
are not universally resolved or bounded by this architecture.

Only after Product accepts custody qualification should the separate wrong-pipe
continuation control, A2-16 health-probe resume and A2-17 runtime-watchdog control
be considered. Their potential three-attempt budget remains separate and unreleased.
No merge, release, tag or binary publication is authorised by this report.
