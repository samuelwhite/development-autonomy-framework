## Diagnosis and bounded repair

The historical `m21a-repair-03` run stopped after 54 passes, before launching
`parent-death-4`. Its original `results.json` and `results.pending` are unchanged.
The pending file contains the same 54 results plus an unconfirmed next case.
The failed publication left that fixed pathname behind; subsequent exclusive
creation of the same file prevented failure-marker persistence. **The original
filesystem exception and Windows error were not retained and remain unknown.**
No antivirus, filesystem, timing or other original cause is invented.

The repair changes only standalone maintainer evidence/acceptance code and tests:

- An exclusive fresh evidence-directory claim permits one writer. Run UUIDs,
  fixed case IDs and ordered sequence numbers bind every record. An existing run
  is refused; interrupted runs are never resumed or automatically qualified.
- Every case starts unconfirmed. Required token, process, cleanup, output and
  case-specific observations are validated before a pass is recorded, and again
  before qualification. The fixed manifest requires exactly the original 55
  unique cases, in order, with distinct package/restricting identities.
- Publication uses uniquely named temporary files containing role, run UUID,
  sequence and nonce. Writes must be complete, flushed, fsynced and read back.
  Strict bounded JSON parsing rejects duplicate keys, malformed/truncated input
  and byte mismatches. Immutable checkpoints preserve earlier valid evidence.
- The primary file is replaced by a same-volume Windows rename using
  `MoveFileExW(REPLACE_EXISTING | WRITE_THROUGH)`, followed by exact readback.
  There is no delete-before-replace, cross-volume copy, fallback or retry.
- A publication failure stops the run and writes an independent uniquely named
  failure record containing sanitized original errno/winerror, stage, run/case
  identity, previous valid checkpoint and current observations. No exception
  message or private path is serialized. If failure retention also fails, the
  process exits unsuccessfully and reports `evidence_retained: false` with both
  numeric error identities; it cannot claim mandatory evidence was saved.
- Final qualification requires all 55 passes and confirmed cleanup. The final
  result and a completion receipt are durably written and read back before the
  active-run marker is removed. An interruption before that commit point cannot
  qualify. `read_qualified` rejects active, pending, failed, corrupt, conflicting
  or incomplete evidence. A bare `qualified` field is insufficient.

Microsoft documents the move flags and error reporting for
[MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw).
Delete-sharing and file permissions can prevent replacement; the
[CreateFileW sharing rules](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)
explain why a live reader can matter. These are possible failure modes, not a
retrospective diagnosis. No transient-error retry policy was needed: each
publication gets one attempt and a persistent failure remains fatal.

This is a maintainer evidence mechanism. It does not implement the M2.1B production
execution journal, admission, authority, recovery or filesystem publication.
The native producer, verifier, harness, readiness parser, IPC, security policy,
source plan, baseline and replacement bindings are unchanged in this repair.

Two publications then succeeded in a separate fresh directory. No native child
was launched. The probe initially expected error 32 and asserted on actual error
5; that mistaken expectation and actual result are retained, with no implementation
change. This does not establish the unknown historical error.

The unchanged native readiness parser's **140 assertions** also pass in the build.
No failure-injection result is counted as one of the native qualification cases.
