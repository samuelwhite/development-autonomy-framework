## Failure and unqualified requirements

Source inspection indicates a harness readiness defect: the probe uses CRT
`printf` for `hold_ready`, which emits CRLF on Windows; the host looks for an
LF-only readiness sequence. The cancellation path depends on that observation.
This is an explanation inferred from source, not a passing cancellation result.
The readiness comparison and failed check were left unchanged. No weakened
requirement, simulated pass or new native test sequence followed the stop.

The failed case's detailed host outcome was not appended before its assertion.
Only the fixed refusal and cleanup were retained. Exact cancellation latency and
termination reason therefore are **not reported as measured facts**. This evidence
handling gap also needs correction before another qualifying run.

Output leakage/overflow, explicit process failure, helper-death and parent-death
cases exist later in the harness but were **not run**. Real forged-success/output
leak containment, inherited-handle bypass acceptance and prelaunch on-disk binary
mismatch controls are not fully qualified. Portable parser checks do not replace
them. The maintainer harness is not a production filesystem broker or admission
controller; final handle-based publication, whole-attempt authority and recovery
remain M2.1B work after a qualified foundation and a separate Product gate.
