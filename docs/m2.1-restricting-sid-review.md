# Second M2.1 isolation investigation: blocked at runtime initialization

30 October 2026. **Feasibility gate remains failed. Stop for Product design review.**

The per-attempt restricting SID survives composition with LPAC and denies the
previous ambient shared-file write in both independent AccessCheck and native
file operations using the final child's token. However, the actual bundled
CPython cannot initialize under either tested restriction policy. These partial
results do not establish a usable execution boundary or preserve the previous
passing Python containment results. No M2.1 implementation has started.

Ambient fixture SHA-256 before and after both final attempts:

It is the same initial fixture content as PR #11, low-integrity with read/write
for `S-1-15-2-2`, and has no attempt-SID grant. The positive fixture demonstrates
that the file-operation probe can actually write when both grants are present.

The native file operations impersonate a duplicate of the actual suspended
child's token. They exercise Windows access checks and real file I/O, but do not
prove that a running Python child has all the required behaviours. The helper
does not resume after an unexpected ambient write. The Python probe likewise
exits immediately if its ambient write succeeds; the runner stops further cases
on an ambient hash change or successful write.

WRITE_RESTRICTED adds a write restriction; it is **not per-attempt read isolation**.
LPAC's read boundary remains separate. The full restriction denies package-only
reads as expected, but also fails earlier in runtime initialization. Neither is
adopted as an execution architecture.

## Compatibility and limits of the evidence

* The documented LPAC token information query returned error 87. It is recorded
  as unavailable, not silently treated as success. Contrasting access checks
  confirm the tested LPAC access semantics remain, including exclusion of
  ALL_APPLICATION_PACKAGES. The whole OS capability surface is not qualified.
* A private newly created desktop and explicit DACLs on the generated token and
  child process/thread did not fix initialization. Existing default desktop and
  window-station permissions were never changed.
* Preliminary named-window-station creation returned error 5. Microsoft documents
  that naming a new station requires Administrators membership. An unnamed
  create-only attempt returned error 183 because the logon station already
  existed. It was not reused or modified as a workaround. No administrator
  dependency was introduced.
* A preliminary debug run loaded ntdll, kernel32, KernelBase, ucrtbase,
  vcruntime140, python314, ws2_32, version, rpcrt4, msvcrt, advapi32, sechost and
  bcrypt, then exited 0xc0000142. A DLL load notification does not establish that
  its initialization succeeded. The exact failing API/DLL and root cause are
  **not established**. This is not proof that Windows universally forbids the
  composition.
* Intermediate builds are recorded as exploratory diagnostics; their source
  snapshots were not retained. They are not used to qualify a boundary. Exact
  source hashes and copied sources are retained for the final two measurements.
* A fixed-size TokenElevation query initially used an oversized buffer and
  returned error 24. The final query uses sizeof(TOKEN_ELEVATION). That harness
  error is separate from the reproduced child initialization failures.
* Independent cleanup checks found that successful DeleteAppContainerProfile
  calls left manually created, empty storage keys. The final harness explicitly
  deletes only the exact storage key it created. Nine earlier empty keys were
  removed after verifying their logged identities and absence of subkeys/values.
  All 15 recorded generated profiles and corresponding storage keys were then
  confirmed absent. The final two runs cleaned their keys without repair.

The existing profile/TEMP/registry read-only ACLs and OWNER RIGHTS protection,
explicit stdio handles, child-process policy and job configuration were retained.
The final job queries report flags 8458 (kill-on-close, process count, process
memory and user-CPU limits), one process, 128 MiB and two seconds user CPU, with
neither breakaway flag. Those configuration checks **do not re-prove enforcement**.

The following must all be run again after any future compatible design: Python
read/stdio positive controls; profile/TEMP/registry create, append and DACL
attacks; private-file/registry and synthetic credential/DPAPI probes; loopback,
TEST-NET and DNS tests; child creation and breakaway; memory/CPU/wall limits;
helper-death and supervising-parent-death termination using retained process
handles. Here they are **not run**, because the initial child cannot reach
Python. No earlier passing result is carried forward as a new pass.

## Design options for a separate decision

1. **Bounded bootstrap investigation, retaining all three boundaries.** Identify
   the precise initialization dependency with source-identified diagnostic
   variants. A candidate change is acceptable only if permissions can be given
   to newly owned objects while preserving the fresh restricting SID, LPAC,
   job and ambient negative test. Reject solutions requiring existing-object ACL
   changes, broad restricting SIDs, administrator privileges, credentials or
   unsandboxed launch. This is the narrowest next research option, not a promised
   fix. It needs a new explicit feasibility decision before more work.
2. **Review a different isolation architecture.** If bootstrap requires ambient
   access that cannot be safely supplied, investigate a stronger separate OS
   security boundary. Any VM or similar design needs a fresh Windows Home,
   prerequisite, installation, resource and lifecycle feasibility assessment;
   it is not approved, selected or claimed to satisfy the no-admin requirement.
3. **Defer execution.** Keep the usable M1.2 read-only planning application while
   the isolation design remains unresolved. Do not relabel a host process,
   profile sealing, tests or a reviewable patch as equivalent isolation.

Do not proceed to an execution controller on the strength of ambient denial
alone. The mandatory trusted exact-byte native review, short-lived single-use
approval, GitHub plan/scope versus local-change provenance, independent producer
and verifier, durable evidence, cancellation and recovery remain requirements
for a later approved design. No imported plan or successful check gains authority.
