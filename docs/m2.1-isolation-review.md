# M2.1 isolation feasibility: stop for design review

30 October 2026. **Gate failed. Execution implementation stopped.**

Product required a standalone LPAC/Job Object/bundled-Python feasibility check
before the wider execution controller, with no unsandboxed fallback. The tested
combination permits an out-of-scope write through an ambient LPAC permission.
No execution controller, native approval UI, journal, producer/verifier adapter,
GitHub execution plan or M2.1 desktop candidate has been added.

## Demonstrated blocker

The helper created a fresh LPAC with only `registryRead`, an explicit handle
list, child-process restriction and a Job Object assigned at process creation.
The child's own package/profile/TEMP and registry were made read-only before
resuming it. The trusted host retained cleanup access. These local restrictions
worked for the tested locations.

The adversarial fixture `ambient-shared.txt` had a low-integrity label and
read/write access for `ALL_RESTRICTED_APPLICATION_PACKAGES` (`S-1-15-2-2`). It had
**no grant for this attempt's AppContainer SID** and was outside its explicit
allowlist. The LPAC worker nevertheless appended:

```text
UNAPPROVED WRITE from feasibility child
```

A fresh sealed-only run measured these SHA-256 values:

| State | SHA-256 |
| --- | --- |
| Before | `260a4e0da0e9317d433048f4eabe82467f3ea1ca5d4164f14179b70f9e9a32ce` |
| After | `c16d2288c2ffb3baa7a3f1b37bc5568d115b426819c10b642d8a3bdbc308d76d` |

The final complete rerun reproduced the write in both baseline and sealed modes;
its before/after hashes are in the [evidence record](evidence/m2.1-isolation-windows.json).
All affected files were synthetic test fixtures under ignored build output.
The proposed documentation correction was **not** applied to the repository.

This is an intended ACL access path, not a claimed Windows vulnerability. The
fixture models pre-existing permissions set by another application or machine
administrator. It does not prove that a particular sensitive stock-Windows file
has those permissions. It does disprove a per-attempt no-write guarantee based
only on the tested LPAC/profile/job configuration. Enumerating or changing ACLs
throughout the user's machine would not be an acceptable remedy.

## Measured behaviour

The environment was a Windows 11 development machine, build 26300.9711 (26H2),
x64, running the helper as a non-elevated ordinary user. This is not clean-machine
or general Windows 11 distribution qualification. The copied application runtime
was PSF CPython 3.14.10, from the existing M1.2 candidate. The native harness was
built with MSVC 14.50.35717, Windows SDK 10.0.26100.0, static CRT, CFG, NX and ASLR.

| Probe | Observed result |
| --- | --- |
| Actual token and job before resume | AppContainer token; LPAC AccessCheck mask excludes ALL_APPLICATION_PACKAGES; one registryRead capability; job membership present |
| Explicit read-only fixture | Read succeeded |
| Unapproved host file / synthetic HKCU value | Reads denied |
| Workspace, copied runtime, host-profile and Windows TEMP writes | Denied |
| Default AppContainer profile/TEMP/own registry | Writes succeeded in the negative control |
| Sealed own profile/TEMP/registry | Create/append and tested permission changes denied |
| Ambient file writable to all LPACs | **Write succeeded outside the allowlist — blocking** |
| Windows version registry value | Read succeeded, as permitted by registryRead |
| Synthetic host Credential Manager entry | Read failed with RPC error 1702; no credential returned; do not relabel this as ERROR_ACCESS_DENIED |
| Synthetic host-user DPAPI blob | Decryption denied with error 5 |
| IPv4 loopback and TEST-NET TCP/UDP | Socket operations denied with error 10013 |
| DNS resolution | Failed with resolver error 11003; this alone is not a packet-capture proof of every possible network API |
| Child process / breakaway attempt | Denied with errors 367 / 5 |
| 160 MiB allocation under 128 MiB process limit | Python MemoryError |
| CPU saturation under two-second user-CPU limit | Kernel termination, exit `0xc0000044`; this is CPU time, not a two-second wall-clock claim |

| Abrupt helper death | Recorded child handle became signalled in about 0.01 seconds |

The final complete suite ran all seven cases: baseline, sealed, memory, CPU,
wall deadline, helper death and parent death. It returned `qualified: false` and
exit 2. A green regression CI check must never be interpreted as overriding it.

## Setup findings and cleanup

* A console-style `CREATE_NO_WINDOW` launch failed during DLL initialization.
  A detached process with explicit stdio handles and `registryRead` ran the actual
  bundled Python. Zero-capability startup did not work on this tested build.
  No network, credential or COM capability was added to the final harness.
* `TokenIsLessPrivilegedAppContainer` returned error 87 on this build. The harness
  records that failure and checks the actual LPAC ACL semantics with AccessCheck;
  it does not silently interpret the failed query as a positive answer.
* A seal placed before process creation was ineffective because creation reset
  profile permissions. A read-only package-SID ACL with explicit host/SYSTEM
  access and OWNER RIGHTS handling was applied after creation, before resume.
* Broad deny ACE experiments obstructed cleanup. Those experiments were removed
  from the final harness. The final ordinary and crash cases cleaned their owned
  profiles. Two exploratory cleanup failures were repaired/retried against their
  exact generated identities; no corresponding profile or registry key remains.

The maintained reproducer is [desktop/isolation](../desktop/isolation/README.md).
The exact final local binary and source-file hashes, runtime hashes, per-probe
outcomes and raw-report hash are preserved in the evidence record. Local raw
traces remain under `dist/m21-isolation-evidence`; binaries and personal paths
are not published. The harness is not production-ready recovery or IPC code.

## Design decision needed

Keep the strict boundary and the accepted deterministic patch-only task. Before
implementing the controller, review an additional kernel-enforced per-attempt
restriction that does not inherit ambient writable LPAC permissions. One
candidate for a separate feasibility design is composing a restricting token
with LPAC and the job, with independent validation of the resulting token and
access checks. This is a research direction, **not a verified fix**: creation
privileges, runtime compatibility, desktop/IPC access, profile/registry cleanup
and crash containment must all be established without administrator setup or
relaxing the boundary. No such composition has been implemented here.

Microsoft documents [LPAC's access model](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer)
and [restricting-token access checks](https://learn.microsoft.com/en-us/windows/win32/secauthz/restricted-tokens).
Those mechanisms are useful design inputs, not evidence that their composition
meets DAF's requirements. The ambient-write reproducer must fail under any revised
design, with the legitimate read/stdio controls still succeeding.

The mandatory approval refinements remain in the [updated proposal](m2.1-supervised-execution-proposal.md):
host-owned exact-byte review, manifest binding, one-use expiring volatile grants,
and explicit separation of GitHub task/scope from locally supplied replacement
bytes. They are not weakened by this isolation finding.

## Delivery boundary

The draft contains feasibility code, evidence and design amendments only. The
public main branch, v0.1 tag/runtime, M1.2 planning interface and original offline
simulation remain unchanged. No provider, spending or execution authority exists
in the desktop. No release, tag, merge, repository security-policy change or
binary publication is part of this work.

Full M2.1 packaged acceptance, trusted-review screenshots, genuine pinned-plan
execution and a new runnable M2.1 review candidate are blocked by this gate.
The existing M1.2 Windows candidate is retained unchanged. Code signing, clean
Windows acceptance and screen-reader qualification remain distribution gates.
Regression validation links will be recorded in the draft PR after CI finishes.
