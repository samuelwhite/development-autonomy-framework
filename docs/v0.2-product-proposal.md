# DAF v0.2: from download to a supervised task

Status: **Product review proposal and offline prototype**, 28 October 2026.
No real provider integration, installation service or execution authority is added.

![Offline Mission Control showing completed milestones, results and usage](v0.2-mission-control.png)

Screenshot rendered from this branch's static HTML in offline Chromium. All data
is fictional, including provider connection, project, task and token reservation.

## Try the prototype

Download this branch's source ZIP, extract it, and double-click
[`prototype/index.html`](../prototype/index.html). It works directly from disk in
a current browser on Windows or Linux. No Python, Node, server, account, internet
connection or configuration edits are needed to use it. JavaScript must be enabled.
The prototype is included in the repository source ZIP, not the v0.1 wheel/sdist.

Choose an assistant (neither is preselected), try its demo connection, choose an
example project and keep **Just give me suggestions**. Setup checks run
automatically. Pick a suggested task and press **Start example task**; no prompt
writing or extra dashboard start is needed. For an approval experience choose
**Make changes, but ask me first** and the documentation task.

Mission Control switches to Overview, Results, Activity and Settings. It shows
milestones, current and upcoming work, attention, usage and recent results. Stop
stays visible while scrolling. Optional demo problems exercise failed setup checks,
quality checks, budget refusal and interrupted connections. Every failure explains
what happened, why it matters and what to do. Setup fixes always run another check;
Retry cannot bypass the failure. Reloading active work holds its allowance and asks
to check the original task, without starting another attempt.

See the [short walkthrough and screenshots](v0.2-ux-walkthrough.md). The three starter
tasks have different prepared results. Custom words are displayed, not interpreted;
that option explicitly uses the documentation demonstration. Projects are fictional;
there is no real folder picker or credential field. The tab remembers demo state
using session storage where supported. Closing the tab can discard it; storage is
not a journal, approval receipt or security boundary. If storage is unavailable,
the UI explains that reload resets the demo. **Start over** clears this tab's
history, and is blocked while work is active or its outcome is unknown. Older
prototype state resets to welcome. This does not touch v0.1 journals.

## Proposed journey

| Step | User sees and does | Safe default / recovery |
| --- | --- | --- |
| Download & welcome | Open one signed platform package; “Let's get set up” | No background start, telemetry or provider request |
| Choose provider | Codex or Claude Code, with plain-language account and billing differences | Neither preselected; one explicit choice |
| Connect | Guided provider-managed sign-in or API credential setup | Never ask for an account password; cancel/retry without starting work |
| Choose project | Native folder picker, exact root and repository status | Read-only first; separate worktree before edits; dirty source stays intact |
| Set boundaries | “Just give me suggestions” or “Make changes, but ask me first”; advanced limits in details | Suggestions by default; one task, 5 minutes, zero retries; no shell, tool network, merge or deployment |
| Automatic check | Installation, connection metadata, scope, sandbox and policy checks run without a button | No inference prompt; only interrupt on failure with reason, direct fix, Retry and help |
| First task | Three suggested outcomes, optional custom words, clear next-step summary, then Start | One explicit task consent, distinct from signing in |
| Mission Control | Workspace navigation, project progress, milestones, current/upcoming work, attention, usage and results; persistent Stop | Separate stopping, stopped and unknown; inspect before continuation; no implied background service |

Target: under five minutes **for a supported machine with an eligible account and
provider prerequisites available**. The browser prototype targets three minutes
and demonstrates zero-install evaluation. A new account, missing sandbox, download
time or enterprise approval can exceed five minutes. Do not hide these prerequisites
or advertise a measured installation result before usability trials.

Validate with five first-time users on each supported OS: time from opening the
download to first supervised result, successful completion without terminal use,
ability to identify billing mode, and ability to stop/recover without help. Record
median, slowest completion and blocked setup causes; do not count a simulated
connection as a verified real integration.

## Architecture review and preservation

Reviewed public baseline: `038f1ef` (v0.1 source), `docs/architecture.md`, roadmap,
`contract.py`, `engine.py`, `store.py`, `stop_control.py`, `bounded_ledger.py` and
`preview.py`. The public package is standard-library Python with no runtime
dependencies. The plan validator accepts synthetic authority only. The engine
commits intent before fixture dispatch, uses stable job identity during lookup,
and separates worker output from validator acceptance. The stop gate orders new
admissions; it does not prove remote cancellation. Reservations survive unknown
outcomes. The ledger and progression engine remain separate experiments.

The current roadmap correctly prioritizes proposal provenance, bounded transports,
owner authority and safe continuation. Add a graphical entry point ahead of live
activation; none of those gates disappear. This branch adds only a sibling
`prototype/`, design documents, regression tests and links. It does not import or
modify the runtime, change dependencies/package version, migrate state or alter CI
permissions. The historical release manifest remains historical.

```text
This PR: browser UI --> deterministic in-memory fixture
                       (no route to the Python runtime)

Proposed later:
local UI --> typed local bridge --> DAF admission / journal / stop / reservations
                                        |
                                versioned provider adapter
                                        |
                             isolated provider child process
                                        |
                              independent result verification
```

Prefer one packaged local application and one controller process. Reuse Python
for the controller; spike a thin system-webview shell and bundled runtime before
committing to a framework. Windows WebView availability and Linux WebKit packaging
need installer evidence. Do not make users install Node, Python, Docker or WSL for
the basic review experience. WSL may be an explicitly explained advanced requirement
for a Claude shell-enabled mode, not a silent prerequisite. Avoid a broker, cloud
account system, always-on daemon or remote dashboard in this iteration.

A real bridge must expose typed operations rather than arbitrary shell commands.
Use private IPC owned by the app; if loopback HTTP is selected, require strict
origin/host validation, ephemeral authentication, CSRF protection, restrictive
binding and no credentials in URLs. Browser-origin checks alone do not establish
owner authority. Keep provider processes unable to write authority, stop or ledger
state. Session storage from this prototype must never be migrated into live state.

## Smallest safe implementation sequence

| Slice | Deliverable | Gate before proceeding |
| --- | --- | --- |
| 1. This draft | Offline wizard, dashboard and contract | Product walkthrough; v0.1 regressions remain green |
| 2. Package the same fixture | Windows/Linux launchable app, native folder picker, safe local settings | Clean-machine install/uninstall, accessibility and measured five-minute trial; no provider subprocess |
| 3. Adapter preflight | Pinned adapter versions, capability negotiation, fake protocol transcripts | Offline auth cancellation, approval expiry, event duplication, crash and stop tests; no real auth |
| 4. Connection-only pilot | Explicitly authorized provider install/login and non-inference verification | OS credential storage, isolation and environment sanitization reviewed; credentials never enter UI logs |
| 5. Codex review-only pilot | One manually started task in disposable checkout via app server | Joint authority/stop/ledger admission review, finite in-flight exposure proven, exact-version OS conformance and separate live/spend authorization |
| 6. Claude review-only pilot | Same UI/contract through Python Agent SDK | API billing consent; third-party auth eligibility; filesystem isolation for all tools; no native Windows shell fallback |
| 7. Supervised edits | Exact diff approval, independent checks, explicit recovery | Stale/replayed approval refusal, protected paths, stop races and unknown usage verified on both OSes |

Do not enable paid execution just because a provider reports usage. If whole-run
financial exposure cannot be bounded to the admitted policy, live activation stays
blocked. No automatic correction loop is needed for the first pilot. Provider
installation, login and a paid task remain distinct actions. All slices after this
draft are recommendations, not actions authorized by this PR.

Local models fit the same capability contract later. An Ollama endpoint alone is
not a development agent: it supplies inference, while DAF would still need a reviewed
tool loop, isolation, accounting and cancellation. No Ollama installation or daemon
discovery belongs in this slice.

Product decisions: accept review-only as default; accept API-only Claude setup unless
provider approval permits otherwise; approve measuring the five-minute target with
prerequisites disclosed. Engineering blockers are detailed in the
[feasibility assessment](v0.2-provider-feasibility.md) and
[provider contract](v0.2-provider-contract.md).

See the [validation record](v0.2-validation.md) for exercised behavior and limits.
